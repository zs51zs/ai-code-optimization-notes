## 一、先记住这四句话

| 论文 | 最短总结 | 主要优点 | 主要局限（就本项目而言） |
|---|---|---|---|
| **SWE-Perf** | 告诉我们**怎样判断优化是否真正有效**。 | 真实仓库任务、明确原始版本/专家补丁、正确性与性能分开评价 | 它主要是 Benchmark，不提供完整的新优化决策系统；原任务以 Python 仓库为主 |
| **PerfAgent** | 告诉我们**怎样用运行证据指导下一次修改**。 | Profiler、外部验证器、多轮反馈、最佳正确 Patch 与反投机 | 主要研究反馈循环；多分支探索不是核心关注点 |
| **ShinkaEvolve** | 告诉我们**下一次应该选择哪个历史候选来优化**。 | Archive、父代选择、新颖性过滤、样本效率 | 论文中多项任务并非真实仓库性能加速；评价器需为任务专门配置 |
| **AlphaEvolve** | 告诉我们**怎样组织大规模程序搜索与自动评价**。 | 数据库、历史 Prompt、级联评价、跨组件修改和实际工程应用 | 依赖可执行且可信的评价函数；复杂工业系统的成本与架构不能直接照搬 |

四个关键词：**可信评价 → 性能证据 → 候选选择 → 搜索资源组织**。

## 二、约两分钟研究汇报讲稿（可直接使用）

我们目前关注的是**基于大语言模型的自主代码性能优化**。这项任务和普通代码生成或 Bug 修复有一个重要区别：修改后的代码不仅要保持正确，还必须在真实、可重复的测量下证明性能有所改善。

围绕这个问题，我们重点研究了四篇论文。

**第一篇 SWE-Perf** 解决的是“如何评价”。它从真实开源仓库的历史性能优化 PR 构建 Benchmark，保存原始代码、人类参考补丁和相关测试，并把补丁应用、正确性和性能收益分开评价。它的实验表明，现有模型虽然能够完成不少正确的代码修改，但实际性能优化收益与人类参考仍有差距。这说明**正确生成代码与有效优化性能是两个不同能力**。

**第二篇 PerfAgent** 研究的是“如何利用运行证据”。它在已有 Coding Agent 上增加 Profiler、外部验证和多轮反馈机制，让 Agent 根据真实热点和上一轮实验结果继续修改，而不是只靠阅读源码猜测或者第一次测试通过就结束。它让我们看到：性能测量不仅用于最终评分，也可以反过来指导下一次优化决策。

**第三篇 ShinkaEvolve** 研究的是“如何选择下一条搜索路线”。如果每次只围绕当前最好的代码修改，可能陷入局部最优。它维护一个包含多个候选程序的档案库，通过父代选择、新颖性过滤等机制，在已有成果利用与新路线探索之间取得平衡。

**第四篇 AlphaEvolve** 将这种思想扩展到自动算法发现和真实工程系统。它利用程序数据库、历史上下文、LLM 变异及自动评价器，不断搜索更好的算法，并通过级联评测和受控修改提高搜索效率与可验证性。

我们的后续计划并不是简单复刻这四个系统，而是**先构建一个具有可靠正确性和性能评价能力的最小代码优化 Agent**，然后逐步加入多轮反馈、Profiler 证据和多候选搜索。每加入一个机制，都安排相同任务、可比预算下的对照实验和消融实验，研究它是否真正提高优化成功率和可信性能收益。

进一步值得探索的研究问题是：**Agent 能否根据当前性能瓶颈、候选历史与剩余预算，决定继续细化当前代码、切换搜索分支，还是重新采样性能证据？** 这是我们目前的研究假设，后续还需要文献查新和实验验证。

## 三、30 秒简短版本

我们研究的是 AI Agent 自主代码性能优化。四篇论文形成一条完整技术链：SWE-Perf 研究真实代码优化任务的可信评价；PerfAgent 利用 Profiler 和验证反馈指导多轮修改；ShinkaEvolve 通过候选档案库和父代选择实现多分支搜索；AlphaEvolve 则展示了程序数据库、级联评价和自动算法发现的更完整组织方式。我们计划先建立可验证的最小优化闭环，再分别研究性能反馈和候选搜索，最后通过统一预算下的消融实验，判断二者是否互补，以及是否存在值得深入研究的自适应决策问题。

## 四、两种讲述方式：按论文讲、按 Agent 环节讲

### 4.1 按论文（适合报告文献阅读进度）

SWE-Perf（评价） → PerfAgent（分析与反馈） → ShinkaEvolve（父代与探索） → AlphaEvolve（搜索基础设施与工程应用）。

### 4.2 按系统环节（适合报告我们计划做什么）

```text
输入真实仓库与优化任务
   ↓
建立原始基线与正确性约束        ← SWE-Perf
   ↓
分析代码与运行瓶颈               ← PerfAgent
   ↓
选父代/确定修改范围              ← ShinkaEvolve / AlphaEvolve
   ↓
Coding Agent 生成优化 Patch
   ↓
外部构建、正确性测试与性能评价    ← SWE-Perf / AlphaEvolve
   ↓
保存候选、决定继续或切换分支      ← PerfAgent / ShinkaEvolve
   ↓
独立复测，输出最佳正确版本与报告
```

**记忆关键**：SWE-Perf 是评价研究，不是本项目要直接复刻的优化 Agent；PerfAgent 的反馈与 ShinkaEvolve 的多候选是不同维度，可以由统一控制器协作。不能宣称我们已实现或验证这样的融合控制器。

## 五、老师可能提出的问题，以及怎么回答

### Q1：你们是直接把四篇论文的方法拼起来吗？

不是。我们准备先构建**统一可复现的评价底座**，再逐一增加、替换和比较策略。简单集成本身不是创新点；创新性需要来自有明确研究问题的决策机制，并通过文献查新与严格实验验证。

### Q2：既然已有 PerfAgent，为什么还要做自己的系统？

PerfAgent 的论文重点在 Profiler 反馈与多轮细化；我们可以进一步研究，在具有多条候选路径和有限预算时，如何联合利用热点证据与候选历史做搜索决策。但是否真正存在增益，需要先与已有方法对照，不能预设结果。

### Q3：为什么还要看 ShinkaEvolve/AlphaEvolve？

单条改进路径可能停滞。两篇进化研究提供候选池、父代选择和自动评价资源组织的机制。但它们的任务得分并不都等于真实仓库性能优化，必须重新定义我们的正确性和性能评价问题。

### Q4：你们现在已经做出 Agent 了吗？

目前正在梳理工程基础并由 Codex 审查已有系统；**不能在未拿到运行报告前声称已实现或复现**。工程计划是 V0 评价底座、V1 One-shot、V2 多轮反馈、V3 Profiler、V4 多候选、V5 预算感知融合。

### Q5：怎样证明新机制有效？

使用同一批任务、基础模型、测试规则和独立最终复测。先比较单路径与多候选、无/有 Profiler 的 2×2 实验，再消融父代策略、采样频率和预算调度；同时报告成本、正确性、真实性能收益与实验波动。

### Q6：为什么需要区分局部加速和整体加速？

局部 Kernel 加速未必使端到端程序同幅度提升；真正的系统指标还受其他阶段耗时影响。应根据任务记录整体耗时及必要的分阶段瓶颈，不能把论文不同量纲的成绩直接比较。
