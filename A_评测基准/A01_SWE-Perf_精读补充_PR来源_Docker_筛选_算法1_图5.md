## 1. 必须区分两套流程

**构建数据集（§3）**：通过 GitHub 历史 PR（人类作者）取得修改前代码及修改后代码，筛选具有稳定性能改善的真实修改；输出原始仓库、测试、环境、专家 Patch 与性能参考数据。

**评测模型（§4–5）**：让模型从原始仓库出发自行生成 Patch，并与专家 Patch 在相同原始基线上的收益比较。构建阶段的人类修改代码**不是** Agent 产生的。

## 2. Docker 和 pytest 各自做什么

- Git/PR：提供人类修改前后的代码版本。
- Dockerfile / Image / Container：定义可复用依赖环境并在容器中执行程序；不同版本的比较应保持资源条件一致，但 Docker 本身**不能消除**宿主机负载、CPU 调频、缓存等噪声。
- pytest：执行原项目的 Python 单元测试，收集 pass/fail 和测试耗时。
- SWE-Perf Phase 2 官方脚本入口：`data_collection/harness/get_runtimes_pytest.sh`（见 data_collection/README.md）；每个代码版本运行 3 轮。
- Phase 2 对容器限制 1 CPU 核与 16 GB 内存；Phase 4 和正式评测使用 5 CPU 核限制；正式评测会重新测量原始版，不直接比较不同时期的旧运行数据。

## 4. Algorithm 1：保守性能收益 δ

输入：`A` 为修改后运行时间样本；`B` 为原始运行时间样本；默认显著性阈值 `alpha=0.1`，步长 `step=0.01`。

每次尝试改善率 `x`，把原始版耗时按比例减小：`B_adj = B * (1-x)`。对 `B_adj` 和 `A` 做单侧 Mann–Whitney U 检验，方向为原始版调整后仍然**更慢**（`alternative='greater'`）。如果 p<alpha，则暂时接受改善率 x 并继续增大 x；一旦检验未通过，停止并返回最后一个通过的 x。

教学演示（**虚构**，每组 10 次测量，未做 IQR 过滤，并非原论文实验）：

- A=[77,79,80,81,82,79,80,81,83,78] ms
- B=[96,98,99,99,100,100,101,101,102,104] ms
- x=0.10：B_adj 典型 90 ms，单侧 p≈0.000088，仍有统计证据。
- x=0.18：B_adj 典型 82 ms，单侧 p≈0.01532，仍通过。
- x=0.19：B_adj 典型 81 ms，单侧 p≈0.11942，不通过；按 1% 步长停止，δ=0.18。

注意：p 不是“优化成功的概率”；δ 不是 95% 置信下界，不是加速比（speedup），而是论文特定检验和搜索规则下的保守收益度量。统计意义不能代替正确性验证。多 Patch 搜索存在测试选择偏差与多重比较风险。

## 5. 图 5 中 Model / Expert 的确切含义

图 5：**只对每个模型产生正确 Patch 的实例计算性能改善**。蓝色 Model 是该模型在其正确实例集合上的平均保守性能收益；紫色 Expert 则在**同一个模型正确实例集合**上，重新计算对应人类 PR 的性能收益。模型不同，正确实例子集不同，所以紫色 Expert 柱不同。这不是 Pass Rate，也不是每个模型对应不同专家。

例：Claude-4-sonnet 在图中 Model 约 2.5%，对应 Expert 约 8.5%；Claude-4-opus 在图中 Model 约 1.6%，对应 Expert 约 10.0%。这些值是各自正确实例子集上的条件平均，不能直接读成“Claude-4-sonnet 在全部 140 题平均改善 2.5%”。

§4 表 2 的总体 Performance 使用全任务数 N_total 为分母；§5.3.1 图 5 将分母替换为 N_correctness（正确样本数），其目的是将“不会生成正确 Patch”与“在正确 Patch 中优化幅度低”区分开。

## 6. 我们的工程和科研启示

1. 评价器应同时追踪：Patch 可应用性、正确性、性能测量、基线与复测环境。
2. “已知优化位置”和“全仓库定位”应分成不同任务设置，避免混淆生成质量与瓶颈定位能力。
3. 需要保存每次测试原始时间序列、代码提交、测试脚本、环境和比较方法；不能只存一个百分比。
4. 参考人类 Patch 并非理论性能上界；报告中应该区分经验基线与最优解。
5. 需要对作者代码继续核查：异常值过滤与 U 检验实现、失败样本记分、单元测试耗时的报告方式，以及正文数量差异。
