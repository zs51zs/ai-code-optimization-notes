## 0. 核心结论（先读）

SWE-Perf 是一个**评价基准**，而不是新的自动代码优化 Agent。它通过“可应用性 Apply → 正确性 Correctness → 可靠性能收益 Performance”衡量对真实仓库的优化。其贡献在于：从真实 PR 中筛出可信任务，保留可执行环境、测试、专家补丁和测量数据，并明确区分“代码改得对”和“代码真的更快”。

**本篇最重要的认识**：一份真实的 Agent 优化结果必须有原始代码版本、候选 Patch、正确性测试、固定工作负载、两侧的原始计时样本和清晰统计方法。模型的自我评价不构成性能证据。

## 1. §3.1 任务定义（Task Formulation）

- **输入**：原始代码仓库 + 目标函数信息。
- **输出**：可应用到原始代码仓库的优化代码或统一 diff Patch。
- **Oracle（文件级）**：根据专家 PR 补丁，用 AST 与 diff 找出专家直接修改的函数，给模型相关文件；较大程度消除了定位难度。
- **Realistic（仓库级）**：提供运行性能相关单测所触及的目标函数，Agent 需要继续定位和修改真实实现，可跨文件；论文使用 yappi 的动态执行信息配合 AST 提取函数，并非完全“零提示”优化未知仓库。
- **潜在泄漏**：不把测试函数本身当优化目标，避免模型为测试数据删除程序功能（test-specific pruning）。

原文：§3.1，§3.2 Phase 5。

## 2. §3.2 真实任务的五阶段构建

| 阶段 | 作者做法 | 设计目的 | 我们能借鉴什么 |
| --- | --- | --- | --- |
| 1 收集 PR | 沿用 SWE-bench 的 12 个热门仓库，收集及筛选 PR；不强制 PR 新增测试 | 找到真实人类改动 | 建立可靠来源和版本快照 |
| 2 测运行时间 | PR 修改前后分别构建 Docker；pytest 记录单测耗时，初始执行重复 3 次，采集阶段限制 1 CPU / 16 GB | 量化差异，统一执行环境 | 原始/修改两侧均记录配置与测量 |
| 3 性能初筛 | 前后版本相关测试均通过；三次平均的改善比例超过 0.3；测试确实覆盖被修改代码；排除 PR 修改的测试 | 去除明显不相关或不可信数据 | 测试覆盖检测 + 禁止篡改评价器 |
| 4 稳定性验证 | 三次测试预热；每项测试重复 20 次；IQR 过滤异常值（k=1）；Mann–Whitney U + 保守收益 δ，保留 δ > 0.05 的测试 | 抑制噪声和偶然收益 | 多次重复、保存原始分布、定义合理停止规则 |
| 5 目标提取 | Oracle：补丁 + AST；Realistic：yappi 动态调用 + AST | 形成可比较的两种优化任务 | 拆分定位能力和代码修改能力 |

**规模（§3.3）**：初始 102,241 个 PR → 阶段筛选 → 最终 140 个实例、9 个仓库。论文同时报告 34,397 个不同代码库、19,499 个成功执行、4,413 个可对比 PR 和 1,696 个中间有效实例。这些数字统计对象不同，**不可拼成单一的同比例漏斗**。

### 2.1 Phase 3 的改善率不是加速比

\[
\mathrm{Ratio} = \frac{R_{\mathrm{original}}-R_{\mathrm{modified}}}{R_{\mathrm{original}}}.
\]

若 100 ms → 65 ms：改善率 = 35%，加速比 = 100 / 65 ≈ 1.54×。这是两个不同的数。阶段 3 的 30% 阈值用于快速初筛，**不是最终评价通过门槛**。

### 2.2 Phase 4 为什么还要统计检验？

一次运行中的负载、CPU 频率、缓存和后台噪声可能造成虚假提升。论文先预热，再做 20 次重复测量，按 IQR 规则删除极端点，对两组样本进行单侧非参数检验。论文使用 α=0.1 与 δ>0.05 作为筛选规则；这些是作者选定的实验参数，不应机械当作通用生产要求。

### 2.3 算法 1：保守最小显著性能收益 δ

输入：A = 优化后运行时间样本；B = 原始运行时间样本。对候选改善比例 x，计算：

\[
B_{\mathrm{adj}}=B(1-x).
\]

对 `B_adj` 与 `A` 进行单侧 Mann–Whitney U 检验：`alternative='greater'`，看“即使基线被人为加速了 x，基线运行时间是否仍显著大于优化版本”。从 x=0 开始，以 step=0.01 增加 x；只要 p<0.1，记录当前 x；第一次不满足时停止。最终记录的 x 即 δ。

**示例（虚构样本，非论文实测）**：

```text
B（原始 ms）=[100,101,99,102,98,100,101,99,100,100]
A（修改后 ms）=[80,81,79,82,78,80,81,79,80,80]
```

使用 `scipy.stats.mannwhitneyu` 的 `alternative='greater'`：

| x | B_adj 的典型数值 | p 值（约） | 判定（α=0.1） |
|---|---:|---:|---|
| 0.10 | 90 ms | 0.00008 | 通过 |
| 0.15 | 85 ms | 0.00008 | 通过 |
| 0.19 | 81 ms | 0.02066 | 通过 |
| 0.20 | 80 ms | 0.51560 | 不通过 |

按 0.01 步长搜索，δ≈0.19（19%）。

**重要边界**：δ 是按特定检验、显著性阈值与搜索步长定义的**操作性保守指标**；不是“优化有 90% 的概率成功”，不是直接的置信区间，也不是理论保证。数据筛选和对多候选反复搜索仍可能产生多重比较与选择偏差。

## 3. §4 三层评价（Evaluation Methodology）

### 3.1 Apply

\[
\mathrm{Apply}=N_{\mathrm{apply}}/N_{\mathrm{total}}.
\]

只衡量补丁能否应用，**不代表构建或语义正确**。

### 3.2 Correctness

每个任务 i 的全部 **性能相关测试**必须通过，任务才记为通过。Correctness = 通过任务数 / 所有任务数。这里不是数学意义的程序等价证明，也不能简单说是“全仓库全部测试通过”。

### 3.3 Performance

论文在正式评价时**重新测试原始版本**，而不是用数据集构建时的旧时间和当前 Patch 时间直接比较。预热、重复运行、过滤离群值之后，计算每个测试 j 的保守改善值 `p_{i,j}`（按算法 1 计算），先对同一任务的测试平均，再对所有任务平均：

\[
P_i=\frac{1}{N_i}\sum_{j=1}^{N_i}p_{i,j},\quad
\mathrm{Performance}=\frac{1}{N_{\mathrm{total}}}\sum_{i=1}^{N_{\mathrm{total}}}P_i.
\]

**不是**平均加速比，不是成功任务百分比，不是直接的样本平均时间改善率。具体失败任务如何计入指标、是否归零，应进一步核对作者 `evaluation` 代码实现（尚未完成逐行验证）。

### 3.4 论文实际结果（Table 2）

在作者实验的 Realistic 设置，Claude-3.7-sonnet + OpenHands：Apply=87.86%，Correctness=77.86%，Performance=2.26%；专家 Performance=10.85%。

**正确表述**：模型的补丁应用和相关测试正确率较高，但保守性能改善仍明显低于专家参考。**错误表述**：“只有 2.26% 的优化任务成功”。

## 5. 对通用代码优化 Agent 的直接价值

1. **评价器与 Agent 分离**：模型生成 Patch，但评价器独立判定可应用性、正确性和性能。
2. **任务规范化**：至少保存代码版本、语言/构建入口、负载、测试、环境、原始与修改后运行时间样本、候选 Patch、错误日志。
3. **先正确再谈性能**：错误但更快的 Patch 不得视作成功优化。
4. **真实重测基线**：同一轮评价同时测量原版本与新版本，避免用过期结果对比。
5. **分层实验预算**：先低成本候选筛选，后重复验证；这是可尝试的工程策略，不等于 SWE-Perf 直接提出的 Agent 搜索算法。
6. **分开诊断失败原因**：定位失败、Patch 应用失败、构建失败、正确性失败、性能无显著提升需分别报告。

## 6. 我们与 Codex 可开展的两个小实验

### 实验 A：验证评价器（工程层）

同一份小型项目及固定输入，准备：正确且变快的 Patch、正确但变慢的 Patch、错误但变快的 Patch、Patch 应用冲突四种情况。要求评价器分别给出正确状态并保存原始样本。

### 实验 B：验证 Agent 定位能力（科研探索）

同一组任务和模型预算，设置：Oracle 给定目标函数、Realistic 给出函数集合、仅提供仓库与工作负载三个难度等级。记录定位准确性、可应用补丁比例、正确性、性能收益及模型调用成本。第三个设置是我们提出的扩展，**不是 SWE-Perf 原始实验设置**。

## 7. 开题研究素材（草案，不作为创新结论）

> SWE-Perf 在真实代码仓库中构建可执行的性能优化任务，并通过补丁可应用性、功能正确性和统计支持下的性能收益进行分层评价，揭示了通用代码智能体在真实代码性能优化上与专家方案之间的差距。其评价体系可为研究性能证据驱动的代码优化 Agent 提供实验依据；进一步的研究需要解决自动定位、测试反馈利用、多候选搜索及评价成本问题。
