两个重要工程问题：

1. **计时可信边界。** LocalRunner接收程序自己打印的runtime/TPS，log Validator也接受程序打印的正确性标志。对于可信已插桩程序有用；对于可改代码的Agent不足以作为正式评分依据。不能靠“不要修改runtime输出”的提示词代替独立计时/输出语义验证。
2. **版本比较契约。** 现有`condition_identity`包含program标识，`_conditions_match`要求其与冻结benchmark一致，这是参数实验的正确约束。后续不能让候选冒用原始commit，也不能放松旧协议来掩盖变化；应新增代码候选评测协议，允许并记录合法源码/产物变化，继续冻结工作负载、工具链、资源、计时/测试及非授权配置。

**以下全部为[方案]；模块名称不是已存在类名。** 建议在现有工具旁新增一条小的代码优化支路，复用记录/执行/统计/报告；不整体重写现有参数与Slurm工程，也不并行引入多个Agent框架。

| 拟建模块 | 最小输入/输出 | 可复用部分 |

| OptimizationTask | 仓库来源、base_commit、允许修改路径、构建/测试/负载、环境、评测协议、预算 | 配置校验思想；须新增代码任务schema |
| RepoWorkspace | base和candidate受控工作树、完整tree/产物指纹、清理/回退结果 | Git inspection仅作探测，不是现成管理器 |

### 5.1 单轮流程与恢复边界

1. 冻结任务、原版、评测器、输入和环境；原版先构建/验证。基线无效即停止，不归罪候选。
2. Agent只看到允许源码、公开测试、当轮性能证据与失败摘要，不看到Expert Patch、隐藏输入或最终确认样本。
3. 生成`candidate.diff`，记录parent与base；先校验修改范围，再在新工作树`apply --check`/应用，保存实际diff。不自动修复不匹配的父版本。
4. 构建、正确性分别运行。失败候选不计性能成功，保存日志/差异；移回原版或已有最佳正确版本，仍可在剩余预算内进行下一轮。
5. 对通过者，用独立评测器重新测原版/候选；Profiler是另一次运行，不把Profiler开销当Benchmark收益。
6. 反馈构建/测试结论、原始计时摘要、噪声、实际成本和新版本热点。错误补丁没有“正确候选热点”或最佳标记。
7. 更新开发期best_observed；结束后对冻结finalist作一次预注册的独立确认。确认通过才给best_confirmed；无确认收益则推荐原版，仍保留正确候选和失败原因。
8. 停止由预算/协议决定；模型STOP不能绕过已提交Patch的构建、测试和评测。中断后可从已持久阶段恢复，但不得从不确定状态猜测“已经测过”。

Git worktree只提供版本隔离，不是安全沙箱。仅有同一OS用户下的目录/文件哈希，不能声称恶意候选无法读取隐藏输入或修改其他文件；需明确可信协作者模式与真正权限隔离的区别。任何清理仅限本系统创建且路径核验通过的工作树，禁止清理用户原树。

### 5.2 数据与成本记录

建议新增候选级对象而不是把所有字段塞入BenchmarkRecord：

```text
Task: task_id, origin, base_commit, workload/test/evaluator/env hashes, protocol
Candidate: candidate_id, parent_id, patch_sha256, tree_sha256, built_artifact_sha256
Stages: apply_status, build_status, correctness_status, measurement_status, decision
Evidence: commands, exit_codes, raw_logs, test_cases, input_hash/seed, individual timings,
          profile_id/version/raw artifact, evidence_ids cited by the model
Agent: provider/model/version, prompt/response hashes, calls, tokens, usage, price_basis
Cost: build/test/profile/benchmark/tool counts, per-stage wall time, total elapsed,
      API cost and currency, measured/estimated/unknown labels
Selection: best_observed, best_confirmed, fallback, stop_reason
```

金额未知用null，不能写0；免费/本地推理也不能把CPU/GPU时间当作免费。重试、失败、无效Patch、测试超时都消耗相应预算。价格需有日期/版本和计费口径，不能用论文平均美元数预测本项目成本。

### 5.3 Profiler首个后端的条件性建议

若采用下节纯Python校准任务，优先试标准库cProfile/pstats以避免当前环境安装/权限阻碍；这只是拟议的后端，**本轮未采集过profile**。它输出的是插桩调用计数/self/cumulative时间，不伪装成py-spy采样数或完整时间顺序调用栈。今后有实际平台条件再选择py-spy、Linux perf或其他适配；不预设Python后端能分析C++ standalone、RDMA或MPI。

## 6. 首次验证任务、评价指标与下一阶段实验方案

### 6.1 首个工程校准任务：TF-01批量词频统计

**[方案]** 建议先建一个独立、小型、标准库依赖的目标Git仓库，而非修改ParallelOpt评测器、hsagent-platform或ParaLedger。目标API为`count_tokens(list[str]) -> dict[str, int]`，保持首次出现顺序、空串/Unicode语义和输入不被修改；CLI只做JSON输入输出。原实现可包含可观测的重复扫描，Agent改动范围仅目标`src/`。

这个目标仓库目前**不存在**，不能说已有真实任务跑通。选择Python仅因为已确认本机解释器/标准库可用，不意味着代码优化流水线已实现。TF-01用于工程闭环与门禁校准，不计为“已在真实开源仓库证明优化能力”。

固定正确性覆盖：空列表、重复/全唯一、空串、中文/非ASCII、不同长度、输入变化、连续不同调用、输出类型/顺序与不变性；规定范围内使用外部参考结果与额外未展示样本。合法缓存需满足状态/失效/内存语义，不一律判作弊。

性能输入先做有界原版校准，调规模至可测但不超时后冻结；分别覆盖不同唯一词比例和分布，不能只挑最易加速的一组。建议最终输入与开发输入分离并跨进程重启。首期计时可用可信父进程测固定端到端命令，输出仍要独立校验；启动开销属于该明确口径，不虚称纯函数耗时。若随后改用函数内计时，必须另订可信边界与协议。

首次**真实仓库**验收应再选择一个纯Python、小依赖的真实历史性能任务，锁定repo/base_commit、公开测试、性能workload及允许改动；可从SWE-Perf实例中筛选，但本轮没有确认可直接运行的具体instance_id。`external/SWE-Perf-reference`是参考工具，不等于已具备目标仓库、依赖环境和隐藏评测材料。若要求第一步就是真实仓库，需要先共同选定/补齐这个任务包，不能编造ID、Expert收益或环境可用性。

### 6.2 门禁必须先通过的对照案例

| 人工控制输入，仅校准评测器 | 应得到的阶段结果 |
|---|---|
| Patch格式/父版本冲突 | apply_failed；不进入构建/计时 |
| 能应用但语法/构建错误 | build_failed；不记为正确或性能成功 |
| 可运行、很快但输出错误 | correctness_failed；保留错误与实际成本 |
| 正确但变慢 | performance_degraded；不替换最佳正确版本 |
| 正确、收益不足或噪声大 | inconclusive；不得写成成功或语义失败 |
| 正确且独立测量支持收益 | performance_confirmed；保留Patch/版本/样本 |
| 最后一轮较慢或错误 | 保留此前最佳正确候选，不能只保存最后一次 |
| 试图修改测试、harness、结果汇总或固定输入 | policy_rejected；不进入正式评测 |

这些例子目前没有对应代码Patch的端到端实现，不能用现有Mock场景数量替代它们。先用脚本化候选校准，再接真实模型；脚本化候选跑通也不能计为AI自主优化成果。

### 6.3 原版、One-shot与反馈方案

下列为待讨论的最小默认方案，不是选定研究算法或立即运行指令：

| 组别 | 候选来源/父版本 | 反馈与选择 | 建议上限 |
|---|---|---|---|
| O：Original / A-A控制 | 同一冻结原版 | 检查评测能否对同版产生虚假收益，不生成Patch | 有界校准一次 |
| S：One-shot | 从原版产生一个模型Patch | 不获得修改后的性能/测试反馈再改；同样经过独立门禁 | 1次候选提交/模型响应 |
| F：反馈迭代 | 最多3个模型候选，记录各自父版本 | 正确性/开发计时反馈；启用Profiler时对其版本重新采集；开发选优 | 最多3次提交/模型响应 |
| K：独立Best-of-3，P2可后置 | 3个候选均从原版独立产生 | 不共享前候选反馈；只用开发可见评测选优，非隐藏Oracle | 与F相同候选上限 |

主比较S/F应给相同的初始仓库信息、公开测试、初始性能证据、模型版本和工具可见性。若F额外有初始Profiler而S没有，测到的是“Profiler+迭代”组合，不应归因仅来自反馈。后续再做F中有/无Profiler或不同摘要方式的消融；本轮不提前建设完整矩阵。

S只有一个候选，不能谎称与F的3个候选严格等成本。报告候选数匹配的K/F对照，以及相同费用/耗时上限下的收益曲线和实际消耗；上限相同不意味着实际费用相同。模型/格式错误和重试均记入调用账本。任何基线都不得使用隐藏测试成绩选Patch。

### 6.4 可执行但尚未启动的测量协议草案

供下一轮确认的数值草案：每个候选开发筛选3个预热配对、5个计分配对；每组最后冻结一个finalist，使用不同输入做3个预热配对、10个计分配对。每个配对对原版与候选使用同一输入/seed，随机并记录AB/BA顺序，串行运行。每次使用新进程；不清系统缓存，不能声称OS级完全冷启动。所有预热、失败和计分原始样本都保存。

开发阶段只作筛选，最后独立确认不再反馈给模型或用于追加搜索。停止规则、超时、异常值处理和实用收益阈值在看候选结果前冻结；建议首次不自动丢离群点。统计方案需在实现前定稿，不能直接把旧三次配对或非配对秩检验包装成新协议的显著性结论。

一种待评审的确认方法：对`d_i=log(T_original_i/T_candidate_i)`作预注册的单侧配对置换检验，并报告`exp(mean(d_i))`及配对bootstrap区间；实用阈值可暂议运行时间减少5%。它是我方实验方案，不是SWE-Perf原指标或已实现代码。检验假设、重复数是否足够、多个方法/任务的比较校正，须在首轮校准后、正式测量前确定；若证据不足，结果为inconclusive，不自动追加样本直至显著。

最多3候选时，上述草案每方法至多48次开发程序调用+26次finalist确认=74次；One-shot为16+26=42次；另计共同A-A校准、构建、测试、Profiler与模型。候选失败时不补足计时额度，也不剔除该失败任务。这里的数字是计划上限，不是本轮执行次数。

### 6.5 指标和验收标准

- 阶段分别报告Apply、Build、Correctness、Measurement、FinalDecision；分母含全部计划尝试，基础设施无效按预注册规则单列，不静默删除。
- `speedup=T_original/T_candidate`，`runtime_reduction=1-T_candidate/T_original`；与吞吐量增长、SWE-Perf保守收益不是同一个百分比。
- 报告任务级原始样本、估计量、波动/区间、确认状态、最佳候选及总成本；正确但无显著加速、显著退化、噪声不足、基础设施失败分开。
- 没有正确候选时，正确子集性能为NA；若将失败对总体计为0贡献，须明确分数定义并另报失败率，不能伪造其运行时间。
- 有Expert时仅独立留作参照，不给生成器看；方法间比较同一任务集合。不同正确子集的Expert均值不得被当作模型排行榜。
- TF-01验收要求：真正生成/保存/应用代码Patch；实际构建和语义测试；外部真实计时；至少一次失败/退化回退；最佳不是最后的情形；每轮版本/证据/预算可重放。工程校准允许没有可确认加速，不能靠预设模拟数值强行“成功”。
- 只有接入真实模型、留下调用轨迹并完成上述链条，才称受控AI代码优化原型；还须在真实仓库任务上验证后，才支持项目真实仓库能力声明。单任务/单次run不支持通用算法优越性结论。

## 7. 实验成本与主要风险

### 7.1 成本口径与可控规模

**[方案]** 首个Agent工程验收可设最多3次候选、总wall-clock不超过20分钟；每次构建/正确性/Profiler分别设明确超时，例如30/30/5秒，超限消耗预算并留日志。这些需任务校准后确认，不是论文最优参数。原版校准总量也应有独立小上限，例如30秒，不能无限放大输入。

若单次程序调用经校准不超过1秒，74次计时调用的程序执行部分上限约74秒；不含启动管理、LLM、构建、测试和Profiler，因此不能作为总耗时或承诺时长。模型费用当前未知，不估美元数；模型、API/本地推理后端、调用与token上限、单价口径均待用户决定。首次正式组间试验可在同一任务上重复3个Agent种子/会话，仍只是可行性探索，成本按实际成功/失败调用累计。

本轮工程内模型/API调用0、构建0、Profiler0、Benchmark0、集群任务0；仅运行第9节的轻量单测，不把其中数值样本称为性能实验。本次Codex对话本身的计费与完整工具耗时未取得，不填0，也不混入未来Agent实验的已测成本。
