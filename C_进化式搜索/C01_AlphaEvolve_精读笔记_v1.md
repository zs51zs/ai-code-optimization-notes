## 0. 一句话概括与研究定位

AlphaEvolve 是一个面向**可自动评价的算法/程序**的进化式 Coding Agent：人类定义目标、初始程序、评价函数；LLM 结合历史代码和评价反馈生成候选修改；系统运行评价、保存候选，再通过程序数据库与 Prompt Sampler 组织下一轮探索。

对我们而言，它的研究价值是：如何把代码候选、执行反馈、搜索历史与有限计算预算结合为可扩展的算法搜索过程。不能将其简化成“LLM 自动重写代码”，也不能直接将其论文算法发现结果当作真实应用性能收益。

## 1. 与前三篇论文的关系

| 论文 | 核心贡献 | 与我们的关联 |
|---|---|---|
| SWE-Perf | 真实仓库优化任务、正确性和性能评价 | 可信评测底座 |
| PerfAgent | Profiler 热点反馈、多轮修复、最佳正确候选 | 运行证据驱动 |

| AlphaEvolve | Prompt Sampler、LLM 集成、Evaluator Cascade、程序数据库、异步流水线 | 搜索调度与系统级算法发现 |

## 2. 论文研究范围与能力边界（§1）

AlphaEvolve 的优势来自“可机器自动打分”这一前提。论文对数学构造、矩阵分解、集群调度、TPU 内核启发式、硬件逻辑、编译器 IR 展示不同应用。缺少可靠评价函数的任务不适合直接照搬。

论文相较 FunSearch 的主要扩展包括：从单个函数到较大代码文件与多组件修改、多个评价指标、丰富上下文、复杂且可并行的高成本评价、使用更强的语言模型。注意“整个 code file”不等于对任何项目无限制安全地修改全部代码。

## 3. 系统总体流程（Figure 1 / Figure 2）

```text
任务定义：初始程序 + EVOLVE-BLOCK + 评价函数 + 可选领域知识
                        ↓
程序数据库（历史代码、分数、执行结果）
                        ↓
Prompt Sampler（选取父代、参考案例、构造上下文）
                        ↓
LLM Ensemble（Gemini 2.0 Flash + Pro；产生代码 diff）
                        ↓
应用补丁，生成 Child Program
                        ↓
Evaluator Pool（校验、运行、评分、级联评价）
                        ↓
结果进入 Program Database，循环
```

### 3.1 任务定义（§2.1）

作者要求用户提供一个评价函数 h，将候选程序映射成标量评价指标字典：

\[h(P)=(s_1,\ldots,s_k)\]

按惯例这些指标越大越好。指标可包含算法目标、性能、质量等，但代码修改的正确性约束应独立定义并且执行。论文的 `evaluate` 通常是固定签名 Python 函数，实际任务可涉及耗时很长的外部训练/搜索过程。

用 `# EVOLVE-BLOCK-START`、`# EVOLVE-BLOCK-END` 限定允许修改的代码区域。初始程序可以很简单，但必须完整可执行。评价器与保护区不应被候选程序任意修改。

### 3.2 Prompt Sampler（§2.2）

Prompt 不仅包含当前代码，还可能包含多个历史程序和它们的评分/输出、领域知识、文献、概率化模板，以及“元提示词进化”所得的建议。作用是让历史搜索证据直接参与下一轮代码生成。

与 PerfAgent 对比：PerfAgent 的主要反馈是性能采样证据；AlphaEvolve 更强调将多代已评价程序和历史发现整合进 Prompt。

### 3.3 Creative Generation（§2.3）

论文主要要求模型输出 SEARCH/REPLACE 形式的精确代码变更，也允许在合适情况下整体重写可进化区域。论文所用模型为 Gemini 2.0 Flash（更大搜索吞吐）与 Gemini 2.0 Pro（部分高质量建议）。不应把该组合理解为经过严格证明的全任务最优配置。

### 3.4 Evaluator Cascade（§2.4）

候选先经过低成本筛选，只有足够有前景时才进入较昂贵的评价阶段；评价器可以支持不同难度的测试、额外的 LLM 质量判断（例如简洁性）及并行执行。对于代码性能优化可考虑：

1. 格式/可应用检查、编译、快速正确性测试；
2. 代表性工作负载初测，检查明显回退；
3. 多输入规模和重复测量、严格正确性与独立最终确认。

上面三段是对我们系统的设计映射，非 AlphaEvolve 原文固定三阶段配置。需要注意：高分并不自动证明语义等价，测试输出应可追溯。

### 3.5 多指标优化（§2.4）

作者认为多个评价维度不仅可同时优化多种目标，也可能让程序数据库保存结构不同但各有优势的候选，从而促进探索。对我们应该把 correctness 作为硬性门禁；运行时间、内存、执行预算可作为指标或约束，而不是将所有量直接加权且忽视正确性。

### 3.6 程序数据库与进化（§2.5）

程序数据库保存历史程序及评分/输出，并使用受 MAP-Elites、Island Model 启发的策略平衡 exploitation 与 exploration。它不是只保留单个最快 Patch。论文公开的是框架描述，不能从这段文本推断某个固定的采样公式。

### 3.7 异步分布式流水线（§2.6）

控制器、LLM sampler、评测节点异步协作，尽量提高预算内候选建议与验证的总吞吐。与“某个单独候选尽快完成”不同。对我们可能引入公平评测队列、失败隔离、资源限制、成本记录，但应在最小可信闭环具备后再扩展分布式吞吐。

## 4. 一轮算法的教学伪代码（非官方源码）

```python
while budget_left():
    parent, inspirations = program_db.sample()
    prompt = prompt_sampler.build(parent, inspirations, task_spec)
    proposed_diff = llm_ensemble.generate(prompt)
    candidate = apply_diff_in_isolated_workspace(parent, proposed_diff)
    if not basic_checks(candidate):
        record_failure(candidate)
        continue
    measurements = evaluator_cascade(candidate)
    program_db.record(candidate, parent_id=parent.id, results=measurements)
return program_db.best_valid_candidate()
```

工程实现仍需：正确性门禁、候选工作区隔离、Patch 回滚、可重复性能测试、实验记录和预算停止策略。

## 5. 论文成果导览（§3；Google 工程细节见第 18 节）

- **4×4 复数矩阵乘法：** 从已知参考的 49 次标量乘法到 48 次。这是数学算法运算次数的改进，不能直接转换成现实程序的加速百分比。
- **Google Borg 调度：** 根据论文生产部署报告，回收约 0.7% 全局计算资源；属于特定数据中心调度策略和负载下的效果。
- **Gemini TPU Kernel：** 论文报告特定 tiling heuristic 对相关 kernel 平均加速约 23%，对应整体 Gemini 训练时间减少约 1%；两个指标分母与作用层次不同。
- **编译器 IR / FlashAttention：** 论文对一个特定配置报告 kernel 部分加速 32%，前后处理部分加速 15%，并非完整应用总体提升同样百分比。

不能把不同任务领域的结果加总或拿来声称本项目已复现。

> 以下新增部分以原始论文 `https://arxiv.org/html/2506.13131` 为依据；图像详见 `https://arxiv.org/pdf/2506.13131` 的 PDF 第 11 页 Figure 4、第 18 页 Figure 8。论文结果不是本研究的复现实验结果。

## 11. 什么是消融实验（Ablation Study）

消融实验指在完整系统中**移除或替换某个特定模块**，其他实验条件尽量保持一致，重新执行相同任务、度量结果差异，从而评估该模块在当前系统及实验条件下的作用。

例如针对自动代码性能优化 Agent，设完整系统包含 Profiler（热点采集）、迭代反馈、多候选池、重复候选过滤。假想的成功率如下（**教学模拟，非任何论文结果**）：

| 设置 | 成功率 | 相对完整系统的差额 |
|---|---:|---:|
| 完整系统 | 60% | — |
| 禁用 Profiler | 42% | -18 个百分点 |
| 禁用迭代反馈 | 35% | -25 个百分点 |
| 禁用候选池 | 48% | -12 个百分点 |
| 禁用重复过滤 | 56% | -4 个百分点 |

`60%-42%=18` 个百分点表明在该假想设置中，加入 Profiler 的完整配置，比去掉它的方案成功率高 18 个百分点；但不能证明所有项目、所有模型上都有同样收益，也不代表独立的 Profiler 具有 18% 的普适收益。

### 11.1 对照实验与消融实验的关系

- 对照实验：比较完整方案 A 与完整方案 B 的效果。
- 消融实验：从一个完整方案出发，控制一个或若干组件开关，分析机制作用。
- 消融本质上也是一种针对系统组件的对照实验。

### 11.2 设计消融时必须控制什么？

1. 相同任务及相同训练/评测数据划分，且结果对相同题目对齐。
2. 相同基础模型、Prompt 约束、正确性规则和性能评测环境（除故意移除的因素外）。
3. 同一预算口径：候选生成数、正式评测数、Token、API 花费、机器时间分别记账。
4. 多个随机种子、报告任务间/运行间波动；不能靠一条曲线下断言统计显著性。
5. 处理实验中变量耦合：关闭一个模块可能改变运行时长、上下文长度、执行路径和候选数量，应予以说明。
6. 观察指标至少区分 Apply、Correctness、Verified Performance Gain 与 Cost。

### 11.3 不能做的错误推断

- 单个模块消融产生的收益不能逐项相加：模块之间可能互补或互相替代。
- 「相同正式评测次数」不代表「总计算费用相同」，因为预筛可能有额外 LLM 调用。
- 「消融版更差」支持该组件在当前设置中有用，但不自动证明该组件是原创创新，或结论可迁移到所有实际仓库。
- 不同数据集/评价分数不能直接比较百分比。

## 12. §3.1：矩阵乘法张量分解的研究任务

给定矩阵乘积 `C = AB`，通过将对应的三阶矩阵乘法张量分解为 R 个秩一张量，获得一个使用 R 次标量乘法的双线性算法。`R` 越低，乘法次数越少；加法、访存等成本并未包含在这个指标内。

二维例子：2×2 朴素矩阵乘法需 8 次标量乘法，Strassen 需 7 次。递归到 4×4，可得 `7×7=49` 次。论文报告 AlphaEvolve 发现复数域上的 `4×4` 乘法的 **rank-48** 分解，而先前特征 0 域该类型分解已知上界是 49。这不等同于 GF(2) 上的 rank-47 结果；也没有证明 rank-48 是该问题的最优下界。

### 12.1 搜索的不是最终矩阵结果，而是寻找分解的程序

作者的初始程序包含：

- 因子初始化器（initializer）；
- 复数张量分解的重建损失（reconstruction loss）；
- Adam 优化器；
- 运行多个随机种子的超参数/初始化测试。

LLM 修改这个 **搜索程序**，得到新的数值优化策略。Evaluator 运行它，检查是否得到更低秩的分解及不同随机种子的成功率。对于候选分解还要做数值取整/半整数化以及精确性确认；不能把一个小的浮点重建损失直接当成数学上完全正确。

### 12.2 Figure 4：真实 Patch 展示了哪些改动？

论文 Figure 4 给出的是最终成功路径上累计的**代码差异与三个局部放大块**，不是 15 张分别对应每轮的截图。论文说该方案经历了 **15 次 mutation**；但 Figure 4 不给出全部 15 次变异逐轮得分。

| 修改位置 | 论文片段中的可见变化 | 为什么可能有用 | 是否已单独因果验证 |
|---|---|---|---|
| 优化器 | 从 Adam 改成带权重衰减的 AdamW | 调整数值搜索轨迹与正则化 | Figure 4 本身不能证明独立收益 |
| 初始化 | 复数初始化尺度缩小，例如代码示例乘 `0.2` | 改变初始搜索分布 | 同上 |
| 损失 | 添加离散化损失，鼓励系数接近整数或半整数；按训练步数调整权重 | 更容易从近似解转向可验证的结构化解 | 同上 |
| 稳定化 | 对大系数、梯度及数值扰动进行处理 | 控制发散并促进探索 | 同上 |
| 超参数搜索 | 加入 `weight_decay`、`discretization_weight`、`target_noise_std` 等参数范围 | 扩大联合搜索空间 | 同上 |

可以把新的训练目标抽象为（**教学概括，非代码逐行数学等价**）：

`L_total = L_reconstruction + λ(t)*L_discretization + β*L_large_values`

其中 `λ(t)` 随迭代进程调整；但代码中还有噪声、裁剪、复杂数值行为，不能仅靠这个简式复现。

**最重要的理解**：模型允许同时修改优化器、初始化、损失和搜索空间，从而有机会获得局部调参无法达到的组合优化；但修改面积越大，评测、回归和归因也就越难。

### 12.3 为什么“15 次变异”不是“只跑了 15 个候选”

一个成功程序的祖先链长度不等于整次搜索生成/评价的候选总数；可能同时存在被拒绝、失败、评分较低的其他分支。论文在 Figure 4 只说明这一例的成功程序涉及 15 次突变，不能据此推断 AlphaEvolve 只花了 15 次 LLM 调用。

### 12.4 研究边界

- rank-48 是代数乘法数上的突破，不代表代码运行时一定按比例更快。
- 较低张量 rank 并不必然带来最好的 GPU/CPU 端到端耗时。
- Tensor decomposition 搜索对数值初始化敏感，应考虑多随机种子。
- 论文还用不同任务和不同评价指标驱动搜索，不能用 rank 指标代表所有性能优化。

## 13. §4：AlphaEvolve 的五类消融，逐项解释

论文在 **矩阵乘法低秩张量分解** 与 **Kissing Number（接吻数）相关球面排布问题** 上开展消融。原文 Figure 8 位于 PDF 第 18 页（0 起始页索引 17）。

### 13.1 Full Method（完整方法）

包含程序数据库/进化、问题上下文、元提示词优化、允许多组件/全文件进化、强弱模型组合。这是各消融比较的参考组。

### 13.2 No evolution（去掉进化）

每次都将**相同初始程序**交给 LLM，而非基于历史较好的后代继续演化。因此它更接近独立多次尝试，不具有把上一代优质修改作为下一代起点的机制。

**验证问题**：收益来自进化积累，还是只是增加 LLM 采样数？

**图中观察**：在左图矩阵分解上，该曲线显著低于完整方法；右图接吻数任务也明显落后。论文支持进化循环的价值，但不意味着任意进化策略都最好。

### 13.3 No context in the prompt（去掉上下文）

去掉显式提供的问题特定上下文，并非必然删除所有任务描述、所有历史程序或改写基础模型。

**验证问题**：有针对性的上下文会不会影响 LLM 提出有效候选？

**图中观察**：两类任务中均弱于完整方法。对我们的启示是：Profiler 证据、历史 Patch、失败原因的表示方式值得单独研究。

### 13.4 No meta prompt evolution（关闭元提示词进化）

仍然可以运行程序搜索，但不自动进化/优化用于指导 LLM 的元提示词。

**验证问题**：优化“如何提问/如何组织研究建议”，是否有额外价值？

**图中观察**：左图矩阵分解中弱于完整方法；不应宣称右图对这项因素也做了独立比较。

### 13.5 No full-file evolution（只允许进化 loss function）

在矩阵张量分解任务上限制可修改范围：只修改 loss function，而非允许同时修改优化器、初始化等更多代码。

**验证问题**：跨模块联合改动相较单个函数改动是否有帮助？

**图中观察**：左图弱于完整方法。需要注意这不能证明无限制修改整个仓库永远更好，真实仓库还需保护接口与正确性约束。

### 13.6 Small base LLM only（仅用一个较小模型）

取消强弱模型混合，只使用单个小基础模型。

**验证问题**：模型能力/模型集成选择对最终搜索贡献有多大？

**图中观察**：左图弱于完整方法。这个消融同时改变模型能力与组合方式，不能严格分离“强模型能力”与“模型集成”各自贡献。

## 14. 如何阅读 Figure 8：坐标、阴影、结论边界

**横轴**：`Fraction of compute budget`，意为已用预算占当前实验预定预算的比例；不是具体评测轮次，也不能直接换算成美元、Token 或墙钟时间。比较应确认每个设置的计算分配、预算归一化规则。

**纵轴**：`Target metric (aggregated)`，跨若干目标聚合的评价指标，**越大越好**。它不是“加速百分比”，也不是直接的张量 rank 或接吻数。例如左图 -2 高于 -6，但不代表 rank 为 2 或 6。原文没有提供足以直接逆推每个点具体物理量的公式。

**阴影**：论文描述为三个不同随机种子独立运行后，目标内标准差的平均表现，**不是95%置信区间**。阴影带是否重叠，不能直接当成严格显著性检验。

左图有 6 条曲线，Full method（绿）整体较高；No evolution（蓝）明显偏低；No meta prompt、Small base LLM、No context、No full-file evolution 位于中间并随预算增加逐步提升。中间几条曲线在部分预算区间接近/交叉，不能宣称存在跨所有预算的严格全序。

右图只有 Full method（绿）、No context（红）、No evolution（蓝）三组。不能从右图推断元提示词、全文件进化、模型集成是否具有普遍增益。

原文结论是每个组件在作者采用的实验设置中有积极贡献；我们更审慎的结论是：**作者给出了可重复实验（3 seeds）支持的任务内证据，但这不是对所有软件优化任务的泛化证明。**

## 15. 结合我们现阶段研究，怎样设计最小消融？

在 Codex 完成 SWE-Perf、PerfAgent 工程审查并实现最小可信闭环后，可以考虑：

1. One-shot：同任务一次生成候选、正确性验证和性能复测。
2. Feedback-only：固定候选链、每轮获得正确性和耗时反馈。
3. Feedback + Profiler：在相同工作量约束下加入结构化热点证据。
4. Population-only：保留多父代，但不给额外 Profiler 证据。
5. Population + Profiler：检验反馈机制与搜索多样性的组合效果。

核心评价：Apply、Correctness、Verified Performance Gain、Cost-to-Target、候选生成数/正式评测数、被拒绝重复数、不同输入规模和不同随机种子结果；采用相同任务、独立验证与可比预算。

最后区分两类假设：

- **方法有效性**：引入某一组件是否能提高可信优化结果？
- **方法互补性**：Profiler 与候选池结合，是否取得超过各自单独效果的额外收益？

第二个问题需要组合消融，不能靠“完整方法好于删掉一个模块”直接证明。

## 18. §3.3 真实工程优化：四个案例的完整精读（2026-11-09 新增）

### 18.1 Borg 数据中心调度（§3.3.1，Figure 6）

**优化对象**：并不是整个 Borg 调度器，而是一个给候选机器排序的启发式评分函数。Borg 已经先判定候选机器是否有能力运行任务；AlphaEvolve 只决定如何对合格机器排序。因此论文把这一部分的调度有效性描述为“correct by construction”。

**问题形式化**：任务有需要的 CPU 与内存，机器有剩余 CPU 与内存；CPU、内存两种资源失衡会产生 stranded resources（搁浅资源）。这可视为在线二维向量装箱问题。论文 Figure 6 中报告的评分函数是：

```python
def alpha_evolve_score(required, free):
    cpu_residual = required.cpu / free.cpu
    mem_residual = required.mem / free.mem
    return -1.0 * (
        cpu_residual + mem_residual
        + mem_residual / cpu_residual
        + cpu_residual / mem_residual
    )
```

**评价链条**：使用 Google 历史工作负载/资源快照构建数据中心模拟器 → 用其对候选启发式打分 → 使用未参加搜索的近期工作负载测试泛化 → 生产部署后监测。论文报告连续平均回收约 0.7% 的全局计算资源。**这是资源利用率改善，不是某段代码快 0.7%。**

**边界**：内部模拟器和真实工作负载未在该论文中充分开源，因此外部读者无法独立复现实测 0.7%；也不能将“已有约束保证资源可行性”解释成所有业务正确性无需测试。

**对我们**：复杂系统可以先限定只进化一个“正确性边界清楚的策略函数”，用独立调度模拟器测试。对未来 ParaLedger 场景，可探索受限的任务调度/参数选择策略，但不能在没有专项验证时允许修改共识与状态一致性逻辑。

### 18.2 Gemini 训练内核：Tiling Heuristic（§3.3.2，Figure 7）

**优化对象**：JAX/Pallas 矩阵乘法 Kernel 的分块（tiling）启发式，而不是改变矩阵乘法的数学含义。一个大矩阵运算会拆成适合 TPU 计算单元、片上内存和数据搬运的很多小块；不合适的 tile 形状可能影响效率。

**评价链条**：从真实 Kernel 用户采集输入形状 → 一半输入形状用于搜索 → 剩余一半输入形状用于独立泛化测试 → 在真实 TPU 上测量运行时间。论文在这个问题上把基本数学正确性描述为“correct by construction”，因为只改变分块策略，不改变数学运算。

**论文数字**：相对工程专家设计的启发式，相关 Kernel 平均加速约 23%；对完整 Gemini 训练时间的影响约为 1% 缩短。注意两个数字分母不同，不能混淆。

**阿姆达尔定律直观解释**：如果某 Kernel 原本只占整个流程的 p=5%，且优化后速度变为原来的 s=1.23 倍，那么假设其他部分完全不变，整体加速为：

\[S=\frac{1}{(1-p)+p/s}=\frac{1}{0.95+0.05/1.23}\approx1.0094\]

即总体速度只提升约 0.94%。这只是帮助理解的**假设计算**，不是论文真实的 Kernel 时间占比；论文也未在所引段落中给出足够信息反推实际占比。

**对我们**：必须把局部函数/阶段收益与系统端到端收益分开记录；否则 Profiler 发现热点后，Agent 很容易追逐高局部加速而对真实系统总体效果帮助有限。

### 18.3 TPU 电路 RTL 优化（§3.3.3）

**优化对象**：原本已经高度优化的 TPU 矩阵乘法单元中的 Verilog 硬件描述，目标降低面积（area）和功耗（power），同时保持功能正确。

**结果**：AlphaEvolve 发现移除一些不必要位的简单重写；TPU 设计人员对其正确性做验证。论文明确说明，下游综合工具也独立发现了这项具体优化。由此可得出：AlphaEvolve 证明了其能够在 RTL 源码阶段提出有价值的候选，但**不能声称该具体改进只能由 AlphaEvolve 发现，也不能把它简化为通用 CPU 代码的运行时间加速**。

**对我们**：当优化对象发生变化时，评价器也必须变化：RTL 用形式或功能验证和面积/功耗指标；通用程序则用正确性、耗时、内存和系统指标。一个总的 Evaluator API 可以复用，但不能用同一评分函数覆盖所有领域。

### 18.4 XLA / FlashAttention 编译器 IR 优化（§3.3.4）

**优化对象**：Transformer FlashAttention 的 XLA 编译器生成的中间表示（IR），包括 Kernel 和前后处理的低级计算图/调度信息。IR 原本更多用于编译器内部表达和调试，并不面向人类开发者手工改写，因此问题非常具有挑战性。

**验证链条**：每份候选 IR 与未修改的参考版本在随机输入上比较数值结果，最后由人类专家对最终版本做更严格的正确性确认。

**论文结果**：针对一个重要的 GPU 推理配置，FlashAttention Kernel 部分加速约 32%，前后处理部分加速约 15%。不能将二者相加成“总加速 47%”，也不能自动推广到其他模型、GPU 或输入形状。这里提到的专家确认是作者的报告，不代表我们已独立复验。

**对我们**：大模型修改低层程序需要更严格的输出对比与回归测试。对多组件优化必须分阶段记性能，且最终用端到端指标确认收益。

### 18.5 四个工程例子共享的研究方法

| 案例 | 搜索变量是什么 | 保持正确性的方式 | 主要收益指标 | 泛化/部署证据 |
|---|---|---|---|---|
| Borg | 资源排序评分函数 | 先由 Borg 过滤不可用机器；模拟器校验行为 | 回收计算资源 0.7% | 未见过的负载 + 上线监测 |
| Gemini tiling | Kernel 分块策略 | 不改变数学运算；在真实硬件测量 | Kernel 平均快 23%；整体训练缩短 1% | 训练/评估输入形状划分 + 生产部署 |
| TPU RTL | Verilog 位宽/逻辑 | 严格功能检查、专家审查 | 面积与功耗优化 | 设计师确认，集成到后续 TPU |
| XLA IR | 编译器生成的中间代码 | 随机输入对参考输出对比 + 专家确认 | 特定配置 Kernel 快 32%；前后处理快 15% | 特定 GPU 推理配置；非全硬件泛化证明 |

**最值得借鉴的系统性设计原则**：明确可编辑边界；把硬性正确性要求与性能目标分开；将搜索样本和保留测试样本分开；记录局部和端到端收益；最终候选需独立复测/审核。

### 18.6 与我们的研究路线：四篇论文形成的不同职责

- **SWE-Perf**：如何构造可复现的真实代码优化任务，如何将 Apply、Correctness、Performance 分层评价。
- **PerfAgent**：怎样主动收集运行时 Profiler 证据、驱动迭代并保留最佳正确 Patch。
- **ShinkaEvolve**：怎样组织多个已评价候选及其父子关系，进行探索/利用和去重。
- **AlphaEvolve**：怎样允许在受控修改空间内进化代码，用级联与异步评价支持复杂、昂贵的现实任务。

**当前待验证研究问题（非已经成立的创新）**：在固定成本下，动态选择可编辑范围、按热点组织性能证据、按历史收益选择候选父代，能否更稳定地提高端到端可靠性能？

**未来最小验证次序**：先检查 Codex 已有工程 → 可信串行闭环 → One-shot/反馈迭代两组基线 → 分层评价与多任务工作负载 → 多候选搜索/改动范围消融。尚不授权重构大系统。
