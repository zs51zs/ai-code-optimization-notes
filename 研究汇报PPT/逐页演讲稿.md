## 第一部分：研究背景与任务定义（实际第 1—5 页）

### 第 1 页｜面向真实软件仓库的自主代码性能优化 Agent

**讲稿**

各位老师好。今天汇报的主题是“面向真实软件仓库的自主代码性能优化 Agent”。这次是阶段性文献学习和研究路线汇报，重点不是介绍我们已经完成了某个最终算法，而是说明：这个问题为什么值得研究、代表性论文分别解决了什么、它们怎样联系起来，以及我们后面准备如何开展工程和方法研究。

首先明确我们的研究对象：输入不是一段让模型从零编写的题目，而是一个**已经存在的代码仓库**，里面有源码、依赖、测试以及特定的性能工作负载。Agent 需要分析程序并生成真实代码修改，也就是 Patch。之后由独立工具构建、执行测试、重复测量性能，再决定接受修改、回退，或者继续优化。最后我们希望交付的是**正确、可以复现、确实有性能收益的代码版本**及其证据。

因此，整个研究的关键词不是单纯“代码生成”，而是“**自主修改 + 外部验证 + 持续决策**”。下面先讲这个问题的背景。

### 第 2 页｜研究背景：软件性能优化为何需要自动化？

**讲稿**

软件性能优化有很直接的工程价值。对计算密集型任务，它影响单位时间完成的计算量；对在线服务，它影响请求延迟、吞吐量和机器资源成本。对于反复执行的高频路径，局部性能改善也可能累积为明显的工程收益。

但实际优化并不只是把一个循环写得更简洁。开发者通常要结合真实工作负载、Profiler、调用链和领域经验，先确认耗时在哪里，再尝试改算法、数据结构或调用方式；每次修改后，还得重新检查正确性与速度。这个过程费时，且很多性能问题跨文件、跨模块，无法只看一个函数判断。

近几年，大模型 Coding Agent 已经能够阅读仓库、定位文件、调用工具并修改代码，为自动化性能工程提供了新的技术基础。但“会改代码”不代表“能把代码优化好”。右侧引用 SWE-Perf 的结果：它构建了来自 9 个 Python 仓库的 140 个优化任务；在其 Table 2 的总体 Performance 指标下，人类参考 Patch 为 10.85%，OpenHands 为 2.26%。这里的数字是**论文定义的聚合性能指标**，不是 OpenHands 只有 2.26% 的正确率，也不是所有任务的平均速度提升倍数。

所以我们的研究动机是：怎样从一次性的模型修改，走向能依据真实测量证据持续改善代码的系统？

### 第 3 页｜研究对象：代码优化 Agent 的任务闭环与成功判定

**讲稿**

这一页给出我们要研究的具体任务形式。首先固定一个原始仓库版本、代表性工作负载、正确性测试、允许修改的范围和搜索预算。这些条件非常重要：如果每个候选使用不同输入或测试环境，后面的性能比较就没有意义。

接着看中间的五个环节。第一步是理解代码和定位瓶颈，可以读取源码，也可以利用 Profiler；第二步由 Coding Agent 提出优化 Patch；第三步构建并运行正确性测试；第四步在可比条件下对原始版和候选版做重复性能测量；第五步根据验证结果做决策：保留、回退或继续搜索。反馈可以沿当前版本继续，也可能在多个候选分支之间切换。

左下方是一个**教学示例，不是我们当前实验数据**：原始版 P0 用时 100 毫秒；P1 用时 82 毫秒且测试通过，但还需要独立复测；P2 只有 70 毫秒，却没有通过正确性测试，所以必须拒绝。这个例子解释了为什么不能只选择数字最小的候选。

我们判断一个优化 Patch 是否成功，至少要关注三个条件：修改后行为符合测试要求；在相同口径下有真实的性能改善；能够回溯代码版本、输入、运行日志和性能样本。接下来看看四篇论文分别为这个闭环提供了什么。

### 第 4 页｜四篇核心论文，分别补齐这个 Agent 的哪些能力？

**讲稿**

这四篇论文并不是四个可以直接互换的 Agent，而是关注不同研究层次。

第一篇 **SWE-Perf** 主要解决“怎样评测”。它构建真实仓库的性能优化任务，并把补丁可应用、功能正确和性能收益分开评价。这里需要强调，它本身主要是 Benchmark 研究，而不是提出一个新的自主优化 Agent。

第二篇 **PerfAgent** 解决“Agent 如何更有效地继续优化”。它在现有 Coding Agent 外面加入性能分析、验证和反馈控制，让模型能够根据真实热点而不是仅凭猜测继续修改，并保留历史上最好的正确补丁。

第三篇 **ShinkaEvolve** 研究“从哪个候选继续”。它维护程序 Archive，选择父代，用 LLM 提出新程序，并通过新颖性过滤和评价管理多条搜索分支。

第四篇 **AlphaEvolve** 更强调通用的程序进化与算法发现框架，使用程序数据库、Prompt Sampler 和自动评价器组织长期搜索。

如果把四篇论文串起来，可以概括为：**SWE-Perf 定义可信评价；PerfAgent 提供运行时反馈；ShinkaEvolve 研究候选搜索；AlphaEvolve 研究更广泛的进化式搜索与评价组织。** 我们不是机械拼接四套系统，而是要研究怎样把这些能力放在同一个可信框架下。

### 第 5 页｜这项研究要如何落地？先有可验证闭环，再研究更好的搜索方法

**讲稿**

这一页是后续工程路线的总览。我们不打算一开始就实现一个功能庞大的进化 Agent，而是通过六个可验收的版本逐步演进。

**V0** 不需要 LLM。给定原始仓库和人工准备的 Patch，评价器能应用补丁、构建、测试、重复测量，并记录结果。**V1** 在这一基础上接入 Coding Agent，形成一次性生成 Patch 的 One-shot 闭环。**V2** 再加多轮反馈，让 Agent 根据失败原因和测速结果继续优化，同时保存最佳正确候选。**V3** 加入 Profiler，让反馈包含函数热点等运行时证据。**V4** 建立多候选 Archive，从不同父代继续搜索。**V5** 才讨论按需 Profiling、级联评价、动态预算和修改空间选择等更复杂策略。

这些 V0 到 V5 是**研究平台的实施阶段**，不是说每个版本都具有独立的学术创新。真正重要的是，在同一任务和可比预算下，用对照实验判断新增机制究竟带来多少改善。下面正式进入第一篇论文 SWE-Perf，先把“怎样测才算优化成功”讲清楚。

## 第二部分：SWE-Perf（实际第 6—9 页）

### 第 6 页｜SWE-Perf：把“代码更快”变成可评测任务

**讲稿**

SWE-Perf 的研究对象是实际仓库中的性能优化，而不是孤立算法题。请看左侧论文 Figure 1。左边给出原始代码仓库和目标函数，中间由语言模型生成 Patch，应用后得到修改版仓库，右边在关联测试上比较原始版、模型版和人类专家版的运行时间。

图里为什么保留 Expert Patch？因为在真实工程中，我们很难预先知道理论上最快的正确实现，但历史开发者确实提交过能改善性能的补丁。它至少说明这个任务存在真实改进空间，并提供一个可比较的人工参照。这里把 Expert 理解为**历史专家实现的参照**更准确，不意味着已证明它是数学意义上的最优解。

另一个关键是：模型面对的不是任意输出一个新程序，而是要产生能应用于指定仓库的代码修改。因此它必须处理仓库结构、依赖、现有测试和代码上下文。

我们后面开发 Agent 时，SWE-Perf 最有价值的贡献就是提醒我们：要先固定任务和版本，建立独立、可重复的正确性与性能评价，才能公平比较不同优化策略。

### 第 7 页｜评价器：Apply → Correctness → Performance

**讲稿**

SWE-Perf 把评测分成三个逐步收紧的层次。**第一关 Apply**：模型提交的 Patch 能否正确作用于指定原始仓库。如果文件路径不对、补丁格式错误或者上下文无法匹配，就连修改后的版本都无法生成，后续测试没有意义。

**第二关 Correctness**：Patch 成功应用后，相关测试是否仍然通过。Apply 成功只表示代码能够被改进去，不代表程序能正常运行。例如把求和逻辑改成取最大值，补丁可能完全能应用，但功能已经错误。测试通过也不意味着形式化证明了所有输入都等价。

**第三关 Performance**：正确的修改是否确实比原版快。SWE-Perf 不是简单测一次时间后比较，而是重复测量，进行预热、异常值处理和统计检验。右侧 Algorithm 1 的思想是：逐步对原始运行时间施加不利调整，检验候选是否仍显著更快，从而得到保守的最小性能收益 δ。论文采用 20 次测量、IQR 去离群值和 Mann–Whitney U 检验等设置。

对我们的系统而言，这三关应由外部评价器严格执行；特别是不能只因为 Agent 自己说“快了”就接受 Patch。

### 第 8 页｜实验设置与主结果：现有 Agent 距专家仍有明显差距

**讲稿**

这页主要看实验条件和 Table 2。论文区分两种设置。**Oracle / File-Level** 提供更明确的相关文件和目标函数，降低定位难度，主要考察模型生成有效优化代码的能力。**Realistic / Repo-Level** 更接近真实 Agent 场景，需要系统自己在仓库中定位、浏览并修改相关代码。

Realistic 下论文比较了两类工作方式：Agentless 是相对固定的多阶段流程，OpenHands 则能够通过工具交互式地探索仓库和迭代修改。它们与 Oracle 的信息条件不同，不能把所有数字直接当成同条件下某种算法的纯粹因果优势。

看下方表格，Expert 的总体 Performance 为 10.85%；Oracle 中列出的模型结果明显较低；Realistic 下 Agentless 为 0.41%，OpenHands 为 2.26%。请注意表格还有 Apply 和 Correctness 两列：Apply 反映补丁能否落地，Correctness 反映功能测试是否通过，Performance 才是性能收益指标。不能把 2.26% 说成 OpenHands 的总体任务成功率。

结论是：现有 Coding Agent 即使具备仓库操作能力，也远没有稳定达到专家水平，因此性能优化专用反馈和搜索方法具有研究空间。

### 第 9 页｜Figure 5：只比较“正确 Patch”后，模型仍远落后专家

**讲稿**

这一页非常容易误读。Figure 5 不再直接使用前一页 Table 2 的全部任务口径，而是**只看某个模型提交且正确性通过的任务子集**，在该子集上比较模型 Patch 和对应的专家 Patch。

因此，图中每一组的蓝色 Model 柱与紫色 Expert 柱，使用的是**同一组该模型已做对的任务**。但是不同模型做对的任务集合可能不同，所以模型 A 的专家柱和模型 B 的专家柱不必相同，也不能把所有蓝色柱子直接当作严格控制任务组成的排行榜。

这一设计回答了一个更具体的问题：排除不能成功应用或功能不正确的情况之后，模型生成的**正确 Patch** 是否已经接近专家的优化质量？从图上看，仍然存在明显差距。页面下方还概述了 Figure 6 对 Oracle、Agentless、OpenHands 工作流的对比，但这些数字同样是正确任务子集上的条件指标，不能与 Table 2 总体指标混用。

这对我们的研究很关键：以后需要同时报告总体成功情况，以及正确候选中的性能收益，并解释两个统计分母。接下来转向 PerfAgent：既然普通 Agent 会遗漏性能机会，运行时反馈能不能改善它？

## 第三部分：PerfAgent（实际第 10—13 页）

### 第 10 页｜PerfAgent：对通用 Coding Agent 增加“性能闭环”

**讲稿**

PerfAgent 的切入点是：现有 Coding Agent 可以修改代码，但容易缺少真实热点证据，在代码看起来能运行时就停止，或者在优化过程中引入回归。作者没有重新训练一个大型语言模型，而是在现有 Coding Agent 外增加控制与反馈机制。

看论文 Figure 1。第一步 **Curated Profiler Usage**：在修改前提供经过整理的热点信息，让 Agent 先看到程序真正在哪里花时间。第二步 **Selective Validation**：生成 Patch 后，运行相关测试，以相对较低的成本拦截错误。第三步 **Measure & Re-profile**：对正确候选重新测速、重新采集热点，让下一轮反馈建立在新版本的事实之上。

最下方的 **Best-patch selector** 也很重要：系统最多尝试若干轮，论文设置上限 θ=5，但最后保留的不是最新 Patch，而是历史中最快的正确 Patch。外部控制器还能处理 Agent 过早 STOP 的问题。

这一页的结论是：PerfAgent 将“模型反复修改”变成一个受外部验证约束的性能优化循环。不过它主要强调单条反馈迭代的质量，而不是系统地维护多条并行搜索路线。

### 第 11 页｜Profiler 证据改变“该优化哪段代码”？

**讲稿**

这一页把 PerfAgent 的两个关键图放在一起。先看左侧 Figure 2：Profiler 采集到的原始调用栈并不适合直接整份塞给 LLM，因此作者先过滤与业务热点无关的栈帧，再解析和聚合热点位置、self-time、total-time、调用上下文及原生库标记，最后生成一份紧凑、可操作的自然语言摘要。

这里 self-time 可以理解为函数自身消耗的时间，total-time 还包括被调函数造成的累计时间。两者的区分有助于判断是本函数本身慢，还是它调用的下层代码慢。摘要只是给 Agent 的输入，原始证据仍需要保留。

右侧 Figure 3 是 `numpy.char.replace` 的实际优化轨迹。第一轮从 Python 层处理开销入手，接着发现更具体的 Python wrapper 问题，随后优化深入 native C kernel。随着代码被改进，最初热点会逐渐减弱，新的瓶颈开始显现。第四轮得到约 **5.87×** 的最佳正确加速，第五轮继续尝试却略有回退，所以最终保留第四轮。

它说明两件事：一是热点定位不能完全依赖静态猜测；二是性能画像必须与代码版本对应，旧画像不能无条件指导新版本。这一点将直接引出我们后面考虑的“证据时效”和“按需重新 Profiling”。

### 第 12 页｜主实验 + 消融：性能收益来自哪些反馈？

**讲稿**

这一页既有主实验，也有消融实验。消融就是在其他条件尽量可比的情况下，去掉或替换一个模块，判断这个模块是否真有贡献。

这里必须特别注意指标口径：论文在 GSO 和 SWE-fficiency-Lite 上报告 Correctness 与 **Hack-adjusted Opt@1**。Opt@1 衡量的是达到指定专家性能目标的任务比例；Hack-adjusted 进一步考虑奖励投机等问题，不能与 SWE-Perf 里定义的总体 Performance 混为一谈。

以页面列出的 GPT-5.1 实验为例，在 GSO 上，完整 PerfAgent 的正确率为 **96.1%**，Hack-adjusted Opt@1 为 **39.2%**；在 SWE-fficiency-Lite 上，对应为 **90%** 和 **74%**。与只有 Loop、Loop+Tests、Loop+Profiler 的变体相比，可以看出 Profiler 与正确性验证的组合对最终可靠收益很重要，但单独增加测试不必然使性能成功率同步上升。

右侧 Best-of-Five 比较也值得解释：简单增加独立候选的数量，可能提高性能成功概率，却需要更多预算；而反馈循环的意义是把前一次执行结果用于下一次修改。论文展示了两者在效果与成本上的差别。

我们的启发不是照搬论文中的百分比，而是在自己的 Benchmark 上采用相同的任务集合、评测规则和清晰的预算口径比较方法。

### 第 13 页｜PerfAgent 对我们的启发：反馈证据必须可信且可追溯

**讲稿**

PerfAgent 提醒我们，性能优化不仅是“快没快”，还涉及证据的可信性。首先，Profiler 摘要应该追溯到原始调用栈和对应的代码版本，避免模型依据被压缩或过时的信息做判断。其次，选择性测试能够降低每轮成本，但它只覆盖被选择的路径；面对 native 代码或复杂依赖，最后仍需要更严格的正确性验证。

还有一个重要风险是 Benchmark 奖励投机。比如模型可能利用固定输入、缓存或者评分流程的缺陷让某个测试数字变得很好看，但并没有获得可泛化的真实优化。因而应区分开发期反馈和最后独立复测，并在需要时测试变化输入。

从工程角度，我们后面希望把 ProfilerAdapter、FeedbackBuilder、CorrectnessGate、LoopController 和 ExperimentStore 分离。这些是我们规划中的可替换接口，不意味着目前代码已经全部实现。

但 PerfAgent 也留下一个问题：如果一个任务存在多条不同的可行优化路线，是否始终沿当前最好 Patch 继续？下面的 ShinkaEvolve 就从**多候选进化搜索**的角度提供了另一种思路。

## 第四部分：ShinkaEvolve（实际第 14—17 页）

### 第 14 页｜ShinkaEvolve：从单一路线升级为“候选群体进化”

**讲稿**

ShinkaEvolve 主要研究的是：在允许 LLM 多次生成程序的情况下，如何提高搜索的样本效率。它不是专门的仓库级运行时间优化 Agent，而是可用于不同自动可评价问题的程序进化框架。

看 Figure 1 左图。系统维护一个包含历史候选及评价结果的 Archive；每次从中采样一个主要父代和参考上下文，由 LLM 生成新程序；在投入昂贵的正式评价前，先尝试用 Novelty Filtering 过滤近似重复或缺乏实质变化的提案；最后执行评价，将候选与结果加入历史记录，继续下一代。

这和只保留一个“当前最好代码版本”的区别非常明显：系统允许多个候选共同存在，也允许较差但有潜力的程序继续作为新的出发点。右侧图展示它在 Circle Packing 问题中的样本效率，作者强调在较少的正式评价次数下也能得到竞争力很强的结果。

这里需要提示听众：Circle Packing 评价的是几何布局目标，不是程序运行时间；因此它证明的是进化搜索能力，不能直接当成代码加速比。对我们最重要的启发，是把“继续修改”转化为“**下一轮选哪个父代继续**”。

### 第 15 页｜三种搜索策略：为什么不是永远选“当前最快”？

**讲稿**

这一页聚焦 ShinkaEvolve 的父代选择。首先是 **Best-of-N**：多次从同一个初始程序独立出发，最后挑选其中最好的。它便于并行探索，但新候选通常不会继承前面候选的局部改进。

第二种是 **Hill Climbing**：始终从当前最高分候选继续修改，能够很快利用已发现的好方法，但也容易反复探索同一片局部区域，陷入停滞。

第三种是论文重点研究的 **Weighted Parent Sampling**。它同时考虑候选的 Fitness 和已有子代数。高得分候选更容易被选择，而已经被开发过很多次的父代会受到一定惩罚。幻灯片下方用 sigmoid 分数和 `1 / (1 + offspring_count)` 表示这个平衡探索与利用的思想；具体官方代码版本的数值归一化细节可能与论文简化公式不同，口头汇报无需把它讲成唯一实现。

这里有两个容易混淆的“新颖性”：一是父代采样时通过子代数量防止反复开发同一父代；二是生成新 Patch 之后，再通过相似度和 LLM Judge 过滤近重复候选。这两个机制处于不同环节。

最后提醒：少评估几个候选不等于整个系统一定省钱，新颖性判断和模型生成同样有成本。

### 第 16 页｜Figure 5：150 次以内的搜索，为什么“分支树”重要？

**讲稿**

Figure 5 是理解 ShinkaEvolve 的关键案例。任务是在单位正方形中放置 26 个互不重叠的圆，让半径之和尽可能大。这个问题有很多局部最优，所以需要搜索不同的算法策略。

请看左图：横轴是已经正式评价的 LLM 程序提案数量，纵轴是进化得到的目标分数。曲线体现了由初始快速改善，到后续探索和局部精修的过程；论文报告，在不足 150 次程序评价内，ShinkaEvolve 得到了超过相关 AlphaEvolve 圆形排布结果的方案。这里的 150 不是“150 秒”，也不是完整系统所有 Token 或计算成本。

右侧是更值得关注的进化树。不同节点代表历史程序，边表示从父代产生子代的关系。历史上的一个候选即使当时不是最高分，也可能提供关键的中间策略，也就是论文所说的 stepping stone，支持后来更好的解。

因此，如果只记录当前最高分，我们会丢掉“一个解是怎样由不同修改路径逐渐形成”的信息。我们之后讨论多候选 Archive，不仅要保存代码与分数，也要保存父子关系和修改历史。

### 第 17 页｜Figure 9 消融：究竟什么让进化搜索更有效？

**讲稿**

这页是 ShinkaEvolve 的消融实验。请先看横轴：三组图都以**已完成正式评价的 LLM 程序提案数量**表示搜索进度，而不是严格相同的端到端成本。

左图比较父代选择。Weighted Sampling 相比始终从原版独立生成的 Best-of-N，以及始终沿最佳候选前进的 Hill Climbing，最终达到更高分数，说明多候选之间合理分配搜索机会很重要。

中间图比较模型策略。不同模型组合和 Bandit-based Prioritization 的区别在于，系统能否根据历史改进情况调整模型使用机会。右图比较新颖性过滤：只依赖模型不断生成，会浪费一些评价在相似程序上；通过 Embedding 阈值和 LLM 判断，可以减少无效正式评价，并在这个实验中改善结果。

但三项结论都有边界：它们首先是在 Circle Packing 等论文任务上得到的，并不直接证明我们的真实仓库 Agent 必须采用完全相同的策略。对我们而言，父代采样、模型选择、新颖性判断都是可以单独开关、单独比较的研究变量。

下一篇 AlphaEvolve 与 ShinkaEvolve 一样有程序进化思想，但它展示了更广泛的算法发现与工程应用。

## 第五部分：AlphaEvolve（实际第 18—21 页）

### 第 18 页｜AlphaEvolve：一个“自动评价驱动”的算法发现 Agent

**讲稿**

AlphaEvolve 是 Google DeepMind 提出的进化式编程 Agent，重点是通过 LLM 修改程序并借助自动评价发现更好的算法。理解这张 Figure 2，最重要的是区分**人类定义问题**和**系统自动搜索**这两层。

图的上方 Scientist / Engineer 提供初始程序、哪些部分允许演化、提示模板、可选的模型以及评价代码。这里评价代码特别重要，因为 AlphaEvolve 并不是让 LLM 自己宣称“我发现了更好的算法”；候选程序必须被执行，得到可以比较的分数。

下方四个模块形成闭环：Program Database 保存历史程序和评价结果；Prompt Sampler 从历史中选择父代与参考候选、组织提示；LLMs Ensemble 生成代码 Diff；Evaluators Pool 执行候选并返回分数。简化流程就是 `database.sample → prompt → LLM 生成修改 → evaluator.execute → database.add`，然后继续下一轮。

因此，AlphaEvolve 的通用性来自**搜索框架与任务评价器分离**。不同问题可以换不同的程序和评分函数，而历史继承与搜索控制的框架可以复用。下面 Figure 4 会说明，它甚至能够改进“寻找算法的程序”。

### 第 19 页｜Figure 4：LLM 能进化“寻找解的方法”，不只是改参数

**讲稿**

这一页是 AlphaEvolve 里面最容易混淆的地方。它研究的是 **4×4 复数矩阵乘法的低秩分解**。朴素矩阵乘法需要 64 次标量乘法，经典递归 Strassen 思路可得到 49 次，而论文通过程序搜索发现了 48 次标量乘法的精确算法。这里的 49 到 48 是**算法使用的乘法次数**，不是在实际 CPU 或 TPU 上测得的速度加快百分比。

为什么原论文 Figure 4 主要显示 AdamW、Loss 和初始化代码，而不是最终的矩阵乘法实现？因为在这个案例里，AlphaEvolve 修改的是**寻找更低秩分解的搜索程序**。搜索程序的初始化、优化器、损失函数、扰动和超参数范围，会直接影响它能否找到更优数学构造。

图中可以抓住三处关键变化：一是优化器从 Adam 调整到 AdamW 等设置；二是 Loss 不只有重建误差，还加入让系数接近某些离散值的约束，帮助数值搜索朝可精确检查的构造靠近；三是初始化和超参数搜索空间也被调整。这些是跨组件的累计改动。论文说明这次成功搜索过程包含 15 次变异，不能根据最终 Diff 断言某一处代码单独导致突破。

这里真正想表达的不是“LLM 会调参”，而是**它能修改寻找解的方法本身**。但更大修改空间同时会带来更复杂的验证和更高搜索成本。

### 第 20 页｜Figure 8：五种消融，回答“为什么需要持续进化？”

**讲稿**

Figure 8 是 AlphaEvolve 的系统消融。消融实验可以理解为：保持整体任务相近，去掉或限制一个机制，看最终表现如何变化。左图是矩阵乘法张量分解，右图是 Kissing Number 问题。横轴是计算预算比例，纵轴是聚合目标得分，越高越好；曲线阴影表示多次运行中的波动。

最重要的对照是 **No evolution**：不继承优秀后代，而是反复从初始程序出发。这个版本明显较差，说明对历史搜索成果的积累与再利用非常关键。其次是 **No context in prompt** 和 **No meta prompt evolution**，分别考察提示词中问题上下文和自动演化提示策略的作用。**Small base LLM only** 用于研究模型组合是否有贡献。

我最关注的是 **No full-file evolution**。在矩阵分解这个实验中，它实际上把可修改空间限制到损失函数，不再允许同时优化初始化或优化器等组件。完整方法更好，支持“跨组件搜索空间可能带来新的算法发现机会”，但并不能推导出“真实仓库允许 Agent 任意修改更多文件一定更安全、更有效”。

还有一个图表边界：**右图只比较 Full、No context 和 No evolution 三种设置**，并不是左图所有消融都在右图重复验证。我们后面若研究动态修改范围，就应当像这篇论文一样用明确的受限版本做对照。

### 第 21 页｜从算法发现到真实工程：每个任务必须设计评价器

**讲稿**

前面两个图看的是数学算法发现，这一页进一步展示 AlphaEvolve 的工程应用。它可以处理 Google Borg 调度、Gemini TPU 内核、TPU 硬件电路以及 FlashAttention 的 XLA 中间表示，但这些任务要优化的对象和评价方法差别非常大。

Borg 调度案例中，系统修改的是机器排序评分函数，并通过历史负载模拟、留出负载和实际部署观察评价；论文报告平均回收约 **0.7% 的计算资源**。Gemini 计算内核的例子优化矩阵分块启发式，论文报告相关内核平均加速约 **23%**，但整体训练时间改善约 **1%**，说明局部 Kernel 的收益不能直接等同于端到端系统收益。

TPU 硬件电路评价还要考虑功能、面积和功耗，并有工程师审查。FlashAttention 的 XLA IR 优化在特定配置下报告 Kernel **32%**、前后处理 **15%** 的加速，这两个数字代表不同部分，不能简单相加。

这四类应用看起来差别很大，但共同点是：**人类明确允许修改的代码区域，并提供任务专属的、可执行的评价器；AlphaEvolve 则在这个边界内反复提出和筛选程序修改。** 这正是我们设计代码优化 Agent 时必须保留的思想。

## 第六部分：四篇论文综合与 Agent 系统设计（实际第 22—26 页）

### 第 22 页｜四篇论文不是四套可替代 Agent，而是覆盖不同研究层

**讲稿**

现在把四篇论文放到同一张工作流里。需要再强调一次，这张图是**我们根据论文总结绘制的综合架构**，不是论文原文已经实现的一套通用系统。

SWE-Perf 提供真实优化任务和可信评价的理念；PerfAgent 告诉我们如何利用 Profiler、测试和运行时间形成反馈闭环；ShinkaEvolve 说明如何通过 Archive 和父代选择探索多个候选；AlphaEvolve 展示如何组织程序数据库、提示上下文和可执行评价资源。

如果对应到下方流程，我们可以把一次优化分成 TaskSpec 定义任务、Analyzer 分析热点、Policy 选定修改起点和范围、Coding Agent 生成 Patch、Evaluator 执行测试与测速、Archive 保存候选和证据、Controller 决定继续还是停止。

整个系统里有两个角色必须分清：**评价器回答“这个 Patch 是否有效”；搜索策略回答“下一次应该尝试什么”**。如果把两者混到同一个模型输出里，后面就很难判断到底是搜索方法好，还是评价条件改变了。下一页因此要专门讲稳定底座与可插拔研究方法的分离。

### 第 23 页｜系统怎么搭建：稳定的实验底座，与可切换的研究策略分离

**讲稿**

这一页是我们工程设计的重要原则。左侧列出五个相对稳定的通用模块。**TaskManager** 负责固定仓库版本、工作负载和预算；**CodingAgentAdapter** 对接现有模型或编码代理，统一输入输出 Patch；**ExecutionSandbox** 提供隔离工作区、构建执行和回滚；**Evaluator** 对正确性和性能做独立验证；**ExperimentStore** 保存候选历史、测量证据和实际成本。

右侧才是我们后面希望不断比较和替换的研究策略，例如：热点来源采用静态分析还是 Profiler；提示中提供源码、热点摘要还是搜索历史；搜索拓扑采用 One-shot、单路径反馈还是多候选；父代选择采用当前最好、加权采样还是证据感知决策；评测资源采用固定测量、级联评价或按需 Profiling。

为什么要这样分？因为如果每增加一种搜索算法就重写一次评价器，我们最后就无法判断差异究竟来自搜索策略，还是代码构建、工作负载或测速方法的差别。所以应尽可能保证相同 TaskSpec、相同 Evaluator 和可比预算，只改变需要研究的策略。

特别说明：这是一份**目标架构设计**，不是宣称当前工程已经具备全部模块，也不意味着模块化本身就能算创新点。

### 第 24 页｜打通“单路径反馈”和“多分支搜索”：一套 Archive，两层循环

**讲稿**

这是我们此前最重要的一个研究思考。PerfAgent 强调根据当前候选的 Profiler 证据持续修改，而 ShinkaEvolve 强调从多个历史候选中选择父代。这两种思想并不冲突，因为它们回答的是不同问题：一个问“**这条分支下一次怎样改**”，另一个问“**下一次应该从哪条分支出发**”。

看左侧的教学示例：原始程序 P0 为 100 毫秒，路线一得到 P1 为 85 毫秒，继续局部优化得到 P2 为 72 毫秒；另一条路线得到 P3 为 93 毫秒，暂时比 P1 慢，但继续发展却得到 P4 为 60 毫秒。如果永远只沿当前最快的 P2 继续，可能会过早丢掉 P3 这条潜在路线。这里所有毫秒数都是**示例，不是论文或我们系统的实测结果**。

右边给出我们拟议的统一控制器。每一轮先从 Archive 中选父代，接着读取**绑定到该父代代码版本和工作负载**的性能证据，再让 LLM 做局部修改。新子代经过构建、正确性验证和性能测量后，连同新证据一起写回 Archive。下一轮可以继续当前分支，也可以切换到其他候选。

因此，融合不是先跑完 PerfAgent 再接 ShinkaEvolve，而是用一个统一搜索循环同时管理**局部反馈和全局分支选择**。但“组合两种已有思想”本身还不是创新；真正待研究的是如何利用证据、历史收益和预算作出更好的切换决策。

### 第 25 页｜先有可信最小闭环，再逐步替换策略：V0 → V5

**讲稿**

这一页把开发计划细化成可以验收的工程阶段。**V0** 是独立评价器，人工 Patch 也要能完成 Apply、Build、Correctness、Performance 和回滚，验证已知正确、错误和退化样例。**V1** 接入模型，一次生成 Patch、外部验证并产生报告，形成最小 One-shot Agent。

**V2** 加多轮反馈和最佳正确候选保存，与 One-shot、同预算独立 Best-of-N 比较。**V3** 加入真正的 Profiler 证据，重点比较有无 Profiler 的改进，而不是同时换模型和评测器。**V4** 加多候选 Archive，比较 Best-of-N、Hill Climbing 和 Population Search。**V5** 才考虑按需采样、级联评价和预算调度等可能形成研究贡献的决策方法。

我们后面提交给 Codex 的工作，应该严格沿着这样的验收关口推进。特别是目前还没形成完整的代码 Patch 评测链，不能因为已经拥有参数搜索和性能统计模块，就认定 V0/V1 已实现。当前最值得做的是先把真实代码修改和可信评价接通，再谈复杂搜索。

这些版本也不是独立论文成果，而是为了后续开展公平实验而建立的平台能力。

### 第 26 页｜如何证明“反馈 × 多候选搜索”的组合确实有效？

**讲稿**

如果我们把 Profiler 和 Archive 都加进去，最终系统变快了，能否说两种机制存在协同创新？还不能。因为提升可能只是试了更多候选、调用了更多模型或做了更多测试。

因此这页提出一个 **2×2 因子实验**。横向比较是否提供 Profiler 证据，纵向比较单路径还是多候选搜索。四组分别是：A，单路径、只有时间与测试反馈；B，单路径加 Profiler；C，多候选、无 Profiler；D，多候选加 Profiler。

A 和 B 比较 Profiler 贡献，A 和 C 比较候选搜索贡献；D 与 B、C 的结果则帮助判断两种机制是否存在额外的组合收益。表中的交互表达式 `I = (D−C)−(B−A)` 是一个用于理解交互效应的示意估计，实际分析还要考虑结果指标是否适合直接作差、任务数、随机波动和统计不确定性。

此外，不能只固定正式候选评价次数，还要记录 Token、Profiler、测试和总体耗时等端到端成本。最终性能需要正确性通过和独立复测支持。这是**未来研究方案**，而不是我们已经做完的实验。

## 第七部分：硕士选题与创新假设（实际第 27—28 页）

### 第 27 页｜七个可选方向：功能可实现，不等于已经形成创新

**讲稿**

最后回到我们的硕士论文选题。前面四篇论文和统一 Agent 架构说明了可能的技术路线，但一个系统能够实现很多功能，并不意味着每个功能都能成为学术创新。

因此我们先整理了七个候选方向。**A** 是性能证据感知的候选分支调度，也就是下一轮从哪个历史程序继续。**B** 是瓶颈迁移与按需 Profiling，研究某个候选的性能画像什么时候可能过时、是否值得重新采集。**C** 是预算约束下的搜索与评价协同，研究成本应该分配给生成、采样、复测还是分支切换。

右侧另外四个方向作为扩展或备选：**D** 根据依赖和风险动态确定修改范围；**E** 强调对未见工作负载的鲁棒性；**F** 研究不同分支之间怎样迁移优化经验；**G** 同时考虑速度、内存与资源等多目标权衡。

当前更推荐的是 **B 作为性能证据层，A 作为搜索决策层，C 提供预算约束**。但这些仍是候选研究问题，尤其与已有 Profiling 引导、进化搜索和预算分配工作存在重叠风险。后续必须阅读 CodeEvolve、BaSE 等更接近的工作，并通过强基线和消融实验确认真正的差异与价值。

### 第 28 页｜拟定硕士论文题目与下一步：先查新、再验证、最后确认贡献

**讲稿**

根据目前阶段性分析，我们暂定的论文题目是《面向真实软件仓库的性能证据驱动的自主代码优化方法研究与系统实现》。题目还需要在查新、工程验证和与导师讨论之后进一步收敛，不能在现在就宣称创新点已经成立。

预期论文工作可以分成三部分。第一部分是**可信的系统底座**：建立真实代码 Patch 的版本隔离、正确性门禁、性能测量和可追溯记录，形成一个能够运行的 Agent 原型。第二部分是希望重点研究的**性能证据感知优化决策方法**：如何为候选建立与代码版本、工作负载绑定的热点状态，判断何时更新画像，并决定下一次继续哪个候选、是否切换分支。第三部分是**多任务、多预算和真实工程场景下的实验验证**，通过强基线、消融、成本统计和失败分析说明方法有效的条件及其局限。

右侧四个关口用来防止研究过早定型：G1 是文献查新，明确与 CodeEvolve、BaSE 等方法的区别；G2 是完成 V0/V1 并确认工程闭环可信；G3 是通过初步实验检验性能证据的时效是否真正影响搜索决策；G4 才是正式的基线、消融、成本与泛化评价。如果主要思路重叠过高或收益不稳定，也要保留向 B+E 或 C+E 等方向调整的可能性。

以上是目前的文献认识和下一步研究路线。我们已经明确了问题与实验关口，但最终的方法创新必须由更充分的相关工作比较和真实实验结果来支撑。我的汇报到这里，谢谢各位老师。
